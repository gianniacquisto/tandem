# Hosted Tandem is one `tandem serve` per workspace behind a control plane

The hosted product is the same binary that self-hosters run. [ADR 0047](0047-serve-is-the-single-door.md) made `tandem serve` the single door for the board, the agents and a remote CLI, so a hosted workspace can be one published `serve` process on its own home, not a multi-tenant service. Every Hosting and `cut` ticket for the hosted product needs one record of that boundary to point at, so each can be refined against a fixed shape instead of re-deciding it.

Decided 2026-11-16 (HOS-19).

## Decision

- **One serve, one home, one workspace.** A hosted workspace is one `tandem serve` process with one home (`tandem.db` plus `bikeshed/`) on its own volume. There is no multi-tenant store: no tenant column, no shared database, no shared process. Isolation is the process and the volume, backups included, so one workspace's backup never holds another's data. The VM or container, the provider, the density and the idle-stop are HOS-17's.
- **The fleet runs the published release, unpatched.** A hosted instance is the public open-source `tandem serve` release, configured only through its documented environment and flags. Anything the service needs from an instance lands in the core as an open feature first, so a self-hoster gets it too: public origin (CUT-37), browser login (CUT-34), members, tokens and roles (CUT-36), export and import (CUT-35), the sign-in handoff (HOS-16) and quotas (HOS-9). "The published release" names the same binary that [ADR 0046](0046-tandem-serve-and-single-binary-distribution.md) distributes. The container image is CUT-28's packaging of that binary, and any amendment to ADR 0046's "one standalone binary" clause is CUT-28's to make, not this record's.
- **The control plane is the service.** It is a separate, closed codebase that the core never depends on. It holds accounts, subscriptions, provisioning state, invites and seats. It stores no ticket or note content, and it is not in the request path for board or `/mcp` traffic, so an instance keeps answering when the control plane is down. This rules out the shape in which a proxy holds the session; the handoff's format is HOS-16's to decide.
- **One truth for access.** The instance's home is the only authority on who may reach a workspace: members, tokens and roles (CUT-36). The control plane's membership (HOS-18, HOS-15) is a derived copy kept for invites, seats and billing, never a second writer. It changes access only by driving the instance through its public interface, and no request is checked against the control plane.
- **The trust boundary, stated honestly.** There is no end-to-end encryption: the board is server-rendered, so the instance reads the content, and the operator can technically read a volume. "Holds no content" is not "cannot reach content". Any credential the control plane holds for an instance is a named, scoped exception, and it never appears in a log, a URL or the image. This record names the open questions and their owners: who mints, stores and rotates an instance's first credential (HOS-17); whether the operator can act as a member, and whether that is recorded if so (CUT-36); and what account deletion does to instance access (HOS-15).
- **The edge.** A TLS terminator maps one hostname per workspace to one instance. It sees plaintext and bearer tokens, so it sits inside the trust boundary and counts as the workspace's infrastructure: it runs in the workspace's region, and for an EU workspace on an EU-owned provider (see 7). The instance port is reachable only through the edge. Workspace origins share no cookie scope with the control plane or with each other. A hosted instance never runs `--allow-unauthenticated`. [ADR 0047](0047-serve-is-the-single-door.md)'s guard gives a public hostname today only what it states: token mode makes no Host check, one shared bearer is one trust domain, `/mcp` admits only a loopback or absent `Origin`, and there is no browser login. Each gap is closed by its ticket: CUT-37 (public origin), CUT-36 (per-member tokens and roles) and CUT-34 (browser login). This record does not design any of them.
- **Region is a choice, and the EU region is the guarantee.** The region is chosen per workspace at creation. Every region keeps the workspace's instance, volume and backups inside that region. The EU region additionally guarantees EU-owned infrastructure for all three (Hetzner, Scaleway or OVH class): data on EU servers, not in the hands of a US-owned cloud. A US region is an option for customers who want US hosting, with no ownership constraint on its provider. The reach of the guarantee is infrastructure only. The payment processor, transactional email and DNS may be US-owned and are named sub-processors, so account data (names, emails, payment details) may reach them. Ticket and note content does not. The public wording and the carve-out list are HOS-11's, and Stripe is allowed (HOS-6). Source hosting and the release registry (GitHub, ghcr.io) carry no customer data and sit outside the rule. Not decided here, and pointers only: whether the US region exists at launch or follows, and which provider serves it (HOS-17); whether regions are priced alike (HOS-1).
- **One control plane, in the EU.** There is a single control plane, assumed to run in the EU on an EU-owned provider (HOS-18 confirms the placement). A US workspace's account data therefore lives in the EU control plane, while its tickets and notes stay in the US region.
- **Region is fixed at creation.** Moving a workspace, to another region or to self-hosting and back, is export and import (CUT-35). There is no replication, no multi-region and no custom domains.
- **Licence boundary.** The core is open source under the repository's licence, and the control plane is closed. The licence change itself is HOS-20's; this record points at it and names no licence as a decision of its own.

## Why

- **The binary is already the boundary.** Because `serve` is the single door, one process per workspace gives each customer the same surface a self-hoster runs. There is nothing to fork for the hosted product.
- **Isolation by process and volume is checkable.** A shared store would need every query to carry a tenant and every backup to be filtered. One home per volume makes the boundary a fact of the infrastructure.
- **A self-hoster gets every hosted feature.** Putting hosting needs into the open core first keeps one codebase and one truth for access, and it stops the hosted fleet from drifting into private patches.
- **The control plane stays out of the request path.** Board and agent traffic never waits on billing or provisioning, and a control-plane outage degrades administration, not the work.

## Rejected

- **A multi-tenant store.** One database with a tenant column puts every customer's content behind one process and one set of queries, so a single defect reaches every workspace and the operator can no longer say where one customer's data sits.
- **A local home that syncs to a hosted one (HOS-2, HOS-3, HOS-4).** Sync was a different shape, a local app syncing to a hosted store. Under one serve per workspace it has no role, so those three tickets close as superseded. No sync record exists, so none is quoted.
- **A proxy that holds the session, with one shared instance identity.** A shared identity makes every workspace one trust domain, and a proxy that holds the session puts the control plane in the request path. Both break the isolation and the outage rule above.

## Consequences

- Each workspace is its own instance to provision, upgrade, back up and delete. HOS-17 owns that operation, and ADR 0047's restart-after-upgrade rule applies to every instance.
- The EU guarantee is an infrastructure claim with named sub-processors, not a claim that no US company touches a customer. HOS-11 publishes the carve-out list, and it must match this record.
- The control plane holds account data for every customer, including US customers, in the EU. Its own security is the account boundary, and it is a closed codebase.
- No behaviour changes. The core's tests stay as they are.
- Sibling records own their parts and are not designed here: HOS-1 (prices), HOS-5 (accounts), HOS-6 (billing), HOS-7 (trust page), HOS-9 (quotas), HOS-10 (operations), HOS-11 (legal), HOS-13 (upgrades), HOS-14 (backups), HOS-15 (teams), HOS-16 (handoff), HOS-17 (provisioning), HOS-18 (control plane), HOS-20 (licence), CUT-28 (image), CUT-34 to CUT-37 (core features).
- Records this one leans on, unamended: [ADR 0009](0009-cli-agent-face.md) (one dispatch), [ADR 0018](0018-rolling-store-backup.md) (the backup file, which excludes `bikeshed/`), [ADR 0045](0045-the-board-and-notes-cut.md) (the work record), [ADR 0046](0046-tandem-serve-and-single-binary-distribution.md) (the binary and the home) and [ADR 0047](0047-serve-is-the-single-door.md) (the single door, its guard and its token mode).
