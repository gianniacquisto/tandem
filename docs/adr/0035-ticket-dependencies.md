# Ticket dependencies: an edge in the store, a derived block on the ticket, and prose only for the reason

Three open tickets carried their dependency in a hand-written `## Blocked on` section (TAN-217, TAN-224, RET-58), and the board could not read any of them. The sprint's batch draw selects on status alone, so a blocked ticket was drawn and then discovered to be blocked by reading the whole body (RET-58 recorded the cost as one slot and four full reads), and the other end is worse: a section that names a person, a release or a credential has no ticket id at all, so no reader can tell when the block has lifted.

The store already had a seam for the relation and no use for it: the schema's rule is **columns are typed, never JSON strings** ([`StoreSchema.swift`](../../Sources/TandemCore/StoreSchema.swift)), and the exception it names is a small ordered list that is never filtered. A blocked list is filtered (the draw reads it) and is read from both ends, so it is a table, not a column.

## Decision

- **A `ticket_dependencies` table, schema v5, one migration, no backfill.** One row per edge: `ticket_id` waits on `depends_on_id`, the composite primary key makes a duplicate impossible, and an index on `depends_on_id` is what the far side reads. Both columns hold the ticket's **UUID**, upper-case as `tickets.id` is written. No foreign key, like every other table here: the store's write is delete-all-then-insert, which a live key would refuse mid-transaction, and the invariants are the core's, as everywhere else.
- **A new table, not a new column.** A read never migrates ([ADR 0031](0031-one-database-the-store.md)), and a new column breaks every read on an un-migrated home; a new table costs one guarded `SELECT` when the version is at least 5. Below 5 every ticket reads with empty lists and nothing else changes.
- **The edge is written in the ticket domain's one transaction.** `writeContents` rewrites the whole ticket domain on every write, so the edges are rewritten with it, from the same in-memory value: `DELETE FROM ticket_dependencies`, the tickets as today, then one row per edge, in the order the ticket's list holds them.
- **Two derived fields on the ticket, filled by the store on every read** the way `ref` is: `blockedBy` (what it waits on) and `blocks` (who waits on it), each a `TicketBlock` carrying the other ticket's id, ref, title and status. `blocked` is computed from the edges and never stored: **a block lifts the moment its blocker reaches `done`, with no write to the dependent**, and an edge to a done ticket stays in the list as history, with its status showing `done`. `blocks` reads in the board's stored order, because the far side has no stored order of its own ([ADR 0006](0006-stored-order-and-sections.md)).
- **The reason stays prose, and is read not copied.** `DescriptionBody.blockedReason` returns the text under a `## Blocked on` line up to the next `## ` heading, line-anchored for `answered`'s reason. No column holds it, so a body a human edits cannot drift from the reason a reader sees. **The prose is never a second predicate**: `blocked` reads edges alone, so a body that still carries the section is not blocked by the store.
- **`block` and `unblock` are the writes.** `ticket block --id <id> --on <id>` resolves both handles through the store's one id rule (ref or UUID) and writes the edge; an existing edge is a **no-op, not an error**, the `complete` rule. `ticket unblock --id <id> [--on <id>]` removes one edge, or all of them. Neither touches status, assignee, `completedAt` or the stored order.
- **Five refusals, each at write time, each with a pinned message**: a ticket cannot block on itself; an edge that would close a cycle names the loop it would make; a done blocker is refused (the block would lift the moment it was written); an archived blocker is refused (the block could never be seen to lift); and an unresolvable handle keeps the store's own `unknownRef` (with the lane's issued range) or `unknownID`. **Archiving a blocker later is allowed**: the state is visible where the block is read, the dependent never draws, and a refusal would hand an app-only human no in-app remedy.
- **A blocked ticket is skipped by the draw, and the skip is named.** The sprint's draw gains one clause (`select(.blocked | not)`), and triage prints one line per skipped row, `skipped TAN-217: blocked by TAN-210 (on-hold)`, which the sprint's first `run` note carries too. The skip is not an error: exit 0, and the batch is short by however many were skipped. `ticket set --status in-progress` does **not** refuse a blocked ticket: [ADR 0017](0017-the-ticket-model.md) validates the value, never the transition, and the draw is the enforcement point.
- **A wait that is not a ticket stays prose, and the ticket is parked `on-hold`.** `on-hold` is already a blocker in ADR 0017's words, the draw already never takes an `on-hold` row, and `blockedReason` still shows the section on `ticket show`. No placeholder ticket: it would be a board row that is not work, drawn and completed like work.
- **It is physical on the ticket's own face**: the board card (a `Blocked, TAN-42` marker line), the list row (a `blocked` capsule), the ticket sheet (`Blocked by` and `Blocks`, each edge clickable, the reason under them, and the far side visible from the blocker's own sheet), and every whole-ticket JSON result. The list summary keeps `blocked`, `blockedBy` and `blocks` and drops `blockedReason` beside the description: the reason is body text, and the body stays out of a list.

## Amendment to ADR 0017's field list

ADR 0017 gives the ticket three axes (Status, Archived, Cycle lane) and two fields that ride along (`description`, `assignee`). A dependency is **not a fourth axis and not a stored field**: it is an edge between two tickets, derived onto each of them as `blockedBy` and `blocks`. Nothing about the three axes, the free-form transitions or the stored order changes.

## Why

- **The board must be able to read a dependency.** Three tickets already carried one in prose, and the sprint paid for it with a slot and four full reads. A relation the store cannot answer is a relation every reader re-derives.
- **The UUID is the key, the ref is the display.** A lane move issues a new number, a lane delete clears it, and a lane key may move while the lane holds no numbered ticket: an edge that stored a ref would silently point at the wrong ticket. Resolving the UUID to its current ref on every read is what keeps `TAN-42` truthful.
- **The simplest state that cannot disagree.** `blocked` is derived, like `done`, so a block lifts without a write and there is no third state to reconcile. The reason is the body's, so the person who writes why and the reader who sees why read the same characters.
- **The refusal is what makes the graph a graph.** A cycle, a self-reference and a dangling ref each break the invariant the draw relies on; catching them at write time means no reader has to defend against them.
- **`on-hold` already answers the non-ticket case.** It exists for "a blocker, a human decision pending, a not now", and the draw already skips it. A placeholder ticket would put a row on the board that is not work.

## Decided against

- **A `blocked_on` column of refs on `tickets`.** It cannot hold a fan-out without a JSON array, which the schema forbids; it cannot answer the far side without scanning every row; and it breaks every read on an un-migrated home.
- **Reusing `tickets.link`.** That column is the Bikeshed note path, written by `setLink` and drawn as the card's paperclip; one column cannot mean two things.
- **Storing refs instead of UUIDs.** A ref moves; an edge that follows it is not the relation the human recorded.
- **A `blocked_on_reason` column.** The reason is the body's section; a column would be a second copy a body edit cannot keep true.
- **A placeholder ticket for a non-ticket wait.** It is a board row that is not work, drawn and completed like work.
- **`ticket set --status in-progress` refusing on a blocked ticket.** The draw is the enforcement point; a refusal here would need its own escape hatch the moment a builder disagrees.
- **Refusing `archive` while a ticket waits on it.** It hands an app-only human a refusal with no in-app remedy, and the state is already visible on both tickets.
- **An author column on the edge, and "only the setter may clear it".** There is no auth on this machine; `assignee` set the precedent that any writer may set any field, and the session record and the comment log say who did it.
- **Topological ordering of the draw.** The stored order is the order ([ADR 0006](0006-stored-order-and-sections.md)); the draw skips, it does not sort, and the batch is five tickets.
- **A `Warning` record type for the skip.** Nothing in the CLI draws; the sprint's line and its record entry are the visible skip.
- **`--blocked` as a three-valued view like `--archived`.** The archive's third value answers "only the archive", a question the block does not have; `--blocked` is a plain AND axis.
- **Editing the block in the app's sheet.** The sheet's Save is one `set`, and an edge write inside it would need its own refusal surface for five messages; the sheet renders, the CLI writes.
- **A dangling edge blocking forever.** A target the store cannot name cannot be shown, so the read drops it, and `delete` removes a ticket's edges on both ends in the same write.
