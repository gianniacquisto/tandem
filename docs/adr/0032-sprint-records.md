# Sprints are records, not tickets: a sprint's own row, handle, batch and close

[ADR 0029](0029-the-ceremony-set.md) made the sprint a ticket: a `Sprint <n> — <lane>` row, `in-progress` while it ran, its description carrying `## The batch`, one `## Run` per landing and a `## Close`. Five sprints ran that way. The convention put a sprint's row on a work board, where every triage pass had to read it and dispatch it like work; it made the number a fact a title had to carry, and the title-derived numbering collided — three of the five archived tickets read `Sprint 1 — Tandem`; and it kept a sprint's history in a ticket description, which the archive swallows and no reader lists without an id. The dead-sprint rule read the title pattern. The human's answer (2026-10-23) settles it the other way: **a sprint is its own record — the session record's shape ([ADR 0027](0027-session-records.md)) applied to sprints — and the app gets its own Sprints tab.**

## Decision

- **A sprint is a record, not a ticket.** One record per sprint, identified by the pair (lane, number), stored in the `sprints` table of the home's one database, `<home>/tandem.db` ([ADR 0031](0031-one-database-the-store.md)). It began as its own `sprints.json` beside the store; ADR 0031's import moved it into the database, so a home whose sprints domain has not written since still reads the file once. A record is never on the board: it carries no brief for triage to refine, moves through no gates, and `ticket list` never shows it. The app's Sprints tab is its face.
- **The handle is the pair (lane, number).** A sprint's human-facing identity is `Sprint 3 — Tandem`, so the lane and the number are its key — there is no UUID on the record. The number is **derived at open**: one more than the highest number the lane's records hold, open and closed alike, `1` on a lane with none. Nobody guesses it and nothing reads it off a title. Numbering is per lane because the lane is in the name; a global number would need a second name to say where it ran.
- **The batch is stored on the record.** `sprint ticket` appends one ticket id per call, deduped and in the order the calls were made; an id the store does not carry is refused, and an id deleted *after* the write reads "not on the board", never an error. The batch is the machine truth, so the per-batch comment on each ticket dies at this switch — a comment would be a second copy of the same fact, and the second copy is the one that goes stale.
- **The run log is a field, dated by the core.** `sprint run` appends one entry, `"<ISO-8601 UTC> — <note>"`; the caller supplies the words, the core supplies the time, so a run entry is dated the moment it was recorded and no later read has to guess.
- **The close is prose, written once.** `sprint close` writes what landed, what slipped and what waits on the human, and stamps `closedAt` in the same write. There is no outcome enum: a session ends in one of four ways and has four words, but a sprint's close is a paragraph that would be flattened by one.
- **The record's whole vocabulary is two states: `open` and `closed`.** The board's six statuses mean nothing here — a sprint is not work on a board — and the two are strict at the reader: an unrecognised state or mode is refused rather than defaulted, because there is no safe default between them.
- **Open creates once, close stamps once, and nothing edits or deletes.** A second `sprint open` on a lane whose sprint is open returns that record unchanged, so re-running the skill's open step cannot fork the sprint; a second `sprint close` keeps the first text and the first stamp. Batch appends dedupe; runs append; there is no edit verb and no delete verb.
- **Six verbs.** `sprint open --lane <name> [--mode serial|parallel] [--session <id>]`, `sprint ticket --lane <name> --ticket <id>`, `sprint run --lane <name> --note <string|->`, `sprint close --lane <name> [--note <string|->]`, `sprint list [--lane <name>] [--status open|closed]`, `sprint show --lane <name> --number <n>`. JSON on stdout: `{"sprints":[…]}` for `list`, the record for the rest. The mode is the human's choice at open, stored; `--session` defaults to `$OPENCODE_SESSION_ID`, and an unset id is a domain failure, the session group's rule.
- **The Sprints tab is the record's face.** The sixth tab, read-only: rows grouped by lane, newest `openedAt` first, and a sheet with the batch, the runs, the close, the opening session and the times. It has no write path — the CLI writes the record, the tab reads it.

## Why

- **The board is for work.** A sprint row crowds every triage pass with a row whose only possible action is "still running", and the first pass that dispatches it as work is doing the wrong job. The board holds tickets; a sprint is not a ticket.
- **The title was carrying three facts it could not keep.** The number, the batch and the history were all in the description, and the number had already collided: three archived tickets read `Sprint 1 — Tandem`. A record derives the number from its lane and holds the batch and the runs as fields, so a reader never parses prose to find out what a sprint carried.
- **The archive swallows a description.** A sprint's history must outlive the archive: the record is listed by `sprint list` whatever the board shows, and its close is read without an id.
- **ADR 0027 already proved the shape.** A session's own record, its own two states, its own tab, and a CLI group of its own replaced `Session —` tickets; the sprint is the same problem with the sprint's facts. Extending the session record instead would have shared one row between a triage session and a sprint, and the lane, number, batch and runs are not session facts.
- **The pair is the identity the human already uses.** `Sprint 3 — Tandem` is how a sprint is named in a report, a close or a conversation; a UUID handle would add a second name to translate.
- **Mid-flight rule (0027's, reused).** This ADR merges in the same PR as the documents it governs — the sprint skill, the build skill's Record step, the glossary and [ADR 0029](0029-the-ceremony-set.md)'s amendment — so there is never a window where the ADR and a skill disagree. Sprints keep being tickets until this merges.

## Decided against

- **Extending the session record with sprint fields** — the human's other option, declined 2026-10-23: a triage session and a sprint session would share one shape, and the lane, number, batch and runs are sprint facts, not session facts.
- **Keeping the sprint ticket and hiding the row** — a sprint stays ticket-shaped, and the description-as-database survives under the board.
- **A `sprint` field on the ticket** — the installed app rewrites the store whole and drops keys it does not know ([ADR 0017](0017-the-ticket-model.md)'s lesson), and it puts a sprint's truth inside a thing the sprint is not.
- **A `sprints` key in the ticket store** — the same erasure hazard that put sessions in their own store; a sidecar beside it, for the same reason, until the one database made every domain a table.
- **The board's statuses** — reusing `in-progress`/`done` would put the record back on the board by another door, and the board's six values say the wrong thing about a sprint.
- **A UUID as the handle** — the human-facing identity is `Sprint <n> — <lane>`; the pair is the handle.
- **A global sprint number** — numbering is per lane today and the lane is in the name; a global number would rename every sprint.
- **An outcome enum on the close** — a sprint's close is prose about what landed, slipped and waits, and one enum would flatten it.
- **Keeping the per-batch comment beside the stored batch** — a second copy of the same fact; it dies at the switch.
- **Migrating the five tickets by hand in the app** — a script is repeatable and reports a mapping; clicks are neither.
- **Shipping the migration as a verb** — it runs once; a verb is a surface to maintain forever.

## Consequences

- **ADR 0029 is amended, not superseded whole.** Its batch decision — "the sprint's batch is a ticket, not a field" — carries a dated pointer to this record; the roster and the minutes are 0029's and stand.
- **The skill changes with the record.** `skills/tandem-sprint/SKILL.md` §3 opens the record (`sprint open`, then `sprint ticket` per batch ticket — the number is derived, never guessed); §4's Record step appends `sprint run`, and the build skill takes the mode from the open instead of a line under `## The batch`; §7 closes with `sprint close`; and the dead-sprint rule reads the record's `session` field and `sprint list --status open` instead of a ticket title, its stale-session signals (an `outcome` and a stale `time.updated`) now read against that session id. The batch-comment line is deleted. Tidy leaves the record alone — it is not a ticket claim to demote — and the roster's minutes line no longer promises run notes in a comment log.
- **The glossary gains Sprint**, and its Avoid line retires "sprint ticket".
- **The five archived tickets move.** `54A38F10`, `401A1E40`, `3A73BCB6`, `080A5A50` (Tandem) and `2AE65AF4` (code-rank) become five records through a one-shot script that is not a shipped verb: the batch from `## The batch`, the runs from the `## Run` sections, the close from `## Close`, `openedAt` = `createdAt`, `closedAt` = `completedAt`, mode `serial`, the opening session where the ticket names one. The records are **renumbered per lane by `createdAt`** — the titles lie, the records do not — and each record's first run entry carries the provenance ("migrated from ticket … 'Sprint 1 — Tandem'"). Nothing is deleted; the tickets stay archived. The proof runs on a copied home, and the run against the real home follows this build's install.
- **No board view draws a sprint row again**, and no comment names a sprint on a batch ticket. A record whose session died is still stale work, found by `sprint list --status open` and settled by the sprint skill's dead-sprint clause, not by triage reading titles.
- **The number.** 0032 is the next free number: 0030 is the ticket vocabulary, 0031 the one database. The sprints decision was first written down as 0030 and renumbered on its own branch when that number was taken — the repo's rule, an older ticket keeps its number.
