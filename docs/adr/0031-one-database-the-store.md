# The store is one database: `tandem.db`, WAL, and an import marker

> **Amended 2026-10-30 by the Rust port (PRT-4):** v1 of the ported schema ships `schema_migrations` alone. `store_imports` arrives with PRT-18's one-off import of the real home, which owns that amendment: there is nothing to import until that script runs, and a marker table no writer writes is a second truth waiting to disagree. The rest of this record stands, including the marker's rule for the domains the port lands later.
>
> **Amended 2026-10-30 by PRT-18, the one-off import of the real home:** **no `store_imports` table ships in the port.** The amendment above said the marker would arrive with this ticket; it does not, and the rest of that amendment stands. The port has no JSON read-fallback for a marker to gate: a v5 file is refused, never read, at the schema seam (`refuse_legacy`, `rust/core/src/store/schema.rs:232`), so "did this domain's import finish?" has no reader whose answer would change. The one import is `Scripts/import-legacy.py`: it writes the whole target store in one run, keeps the source's database as `legacy.db`, and proves the run with its verification mode. A marker table no writer writes would be the second truth waiting to disagree that this record already rules out, with nothing left to disagree with. The marker's rule for the domains the port lands later is untouched.
>
> **Amended 2026-10-30 by the Rust port (PRT-11):** the store gained `store_meta`, one row holding the store's `revision`, and the rpc's change watch keeps one read-only connection for the child's life. The revision is the number every listing and every change event carries: a write that changes a row moves it **inside the write's transaction**, and a listing reads it with its rows in one `BEGIN DEFERRED`, so a payload is never paired with a number a writer moved after it. It is stored rather than derived because the engine offers no shared monotonic counter: `PRAGMA data_version` is per connection and says only that its own view moved, and a number derived from the rows would be a scan that still races the write it describes. The table is the seam's, created by migration v4; a read of an older file answers revision 0 and migrates nothing. The watch connection is the one exception to "a connection per operation": the child is long-lived and polling a fresh connection every tick cost an open and a close 25 times a second. The watch reopens when the path no longer names the file it opened, which is the documented restore below (a rename over `tandem.db`), and backs off to 5 s when the store is refused, so a legacy or unreadable home does not spin.
>
> **Amended 2026-10-30 by the Rust port (PRT-23):** the ported store took a sidecar lock this record had retired: `Store::write` wrapped the whole transaction in `LockedDirectory::for_store(..).with_lock(..)`, so every write serialised on `<home>/tandem.lock` before it reached the engine, and the lock's turn queue grew to make that second serializer fair. The wrapper is gone. `rust/core/src/store/mod.rs` opens the database, runs `BEGIN IMMEDIATE` inside the ~2 s busy window and rolls the backup, with no file lock and no sidecar anywhere on the store's path, which is what this record's "the sidecar lock is retired" clause always said. Two threads of one process queue on a process-local mutex keyed on the canonical home: it is memory, not a file, it dies with the process, and it keeps in-process writers from racing the busy handler (a Windows run answered `Locked` when they did). Across processes the engine's write lock and the busy window stay the bound. `LockedDirectory` stays in `rust/core/src/store/locked.rs` for the bikeshed ([ADR 0004](0004-vault-protocol.md)), the file tree that still needs a sidecar; the store borrows only its temp, its commit and its directory sync for the rolling backup. A `tandem.lock` beside a ported home is inert, exactly as the decision below says.

The store was a JSON file, and its protocol was a set of file tricks: an exclusive `flock` on a sidecar (`~/.tandem/tandem.lock`), a same-directory temp file, an `fsync`, a `rename`, a versioned envelope ([ADR 0001](0001-store-protocol.md)), a rolling copy ([ADR 0018](0018-rolling-store-backup.md)), and a quarantine-and-restart for anything that would not decode. One file per domain grew beside it — `tickets.json`, `comments/<id>.jsonl`, `sessions.json`, `sprints.json`, `settings.json` — each with its own reader, its own recovery path, and no way to ask a question across them. The ask (`6B96343A`) was counts and migrations: tokens, cost, seconds, open and done, answerable as numbers rather than by loading a file; and a home whose first bad write is recoverable rather than a wipe.

We decided: **one SQLite database per Tandem home**, `<home>/tandem.db`, read and written by the app and by every `tandem-cli` invocation, and no second source of truth. The bikeshed stays a folder of markdown: notes are prose, not rows.

## Decision

- **One file, one engine.** `tandem.db` holds every domain — tickets and lanes in P1, comments, sessions, sprints and settings in P2. `schema_migrations` and `store_imports` are the seam's own tables. A connection per operation: every read opens its own read-only connection, every write its own read-write one, and a `busy_timeout` of ~2 s turns contention into the store's existing "locked" domain error ([ADR 0007](0007-locked-directory.md)'s translation rule, at the new seam). A `Store` value stays `Sendable`; there is no shared mutable handle.
- **WAL.** The journal mode is a property of the file. Readers see a consistent WAL snapshot without taking a lock — the read [ADR 0001](0001-store-protocol.md) promised — and writers serialise on the one file. The open sets WAL only when it is not already on: re-asserting it is a write-side operation that answers `SQLITE_BUSY` without consulting the busy handler, which is how the concurrency suite caught a lost update. Two opens racing to create the same home re-check the mode and let the winner's switch stand.
- **`schema_migrations` is the version seam.** One row per applied migration: an integer `version` and the UTC `appliedAt`. Migrations are append-only — a shipped version's DDL never changes; a later change is a new migration. Each runs in its own transaction with the version **read inside the transaction that records it**, so two connections opening a fresh home serialise and apply v1 once instead of the loser dying on a primary key. A migration that throws rolls its transaction back and fails the open loudly; nothing half-applies. v1 (the ticket and sidecar tables) shipped in v0.27.0; v2, the sidecar columns v1's sketch left out, lands with the next build.
- **`store_meta` is the revision's home.** One row, `('revision', n)`, moved by every write that changes a row, inside that write's transaction (PRT-11). A listing reads it with its rows in one read transaction and a receipt reads it before its own commit, so the number a client sees describes exactly the rows beside it. It is not derived: `data_version` is per connection, and counting rows is a scan that cannot be atomic with the write it counts. The first write on a fresh home lands at revision 2, because the migration that creates the table seeds it at 1 in its own transaction; a client treats a listing's number as authoritative and a change event as a hint to re-read.
- **`store_imports` is the import seam, and the marker — not table emptiness — decides.** One row per domain whose legacy file was imported, or for which there was nothing to import, written **in the same transaction as the imported rows**, so "imported" and "has rows" can never disagree. Its `source` is the legacy file's name when one was imported, and `source` is NULL for a fresh home's first write, which found no file; either way the row says "this database is the domain's store", and that is the only question a reader asks of it. Table emptiness cannot be the signal: a database whose first write was killed before its import committed has a schema and no ticket rows, and answering from it would show an empty board beside a file full of tickets — while a home that legitimately holds zero tickets is indistinguishable from it. The marker is durable state read **inside the write transaction**, not a filesystem snapshot taken before the connection, so two first writers import once and neither loses the other's rows.
- **Read-fallback: a read never imports and never writes.** A home with no database, or a database whose domain marker is absent, reads the legacy JSON file — `tickets.json` if it is a regular file, else `todos.json`; a present-but-not-regular `tickets.json` is invalid, never a fall-through for a broken new one. Both names and both key shapes (`tickets`/`lanes`/`lane` beside `todos`/`sections`/`section`) are read **one generation deeper than the rename left them**: the JSON reader outlives the JSON writer, because the imported file stays on disk and a hand-restored copy must still be readable. A fresh home — no database, no file — is an empty store, not an error.
- **Import on the domain's first write.** The write reads the legacy file once, copies it aside as `<name>.pre-sqlite-<unix-ts>` (colliding names suffixed; a copy that cannot be taken fails the write, and a partial copy is removed), then writes the rows and the marker in one transaction. After the commit the file is never read for a write again. The gate is the install, in ADR 0017's sense: the trigger is a build carrying the database reaching the home, not a flag or a click. A kill before the commit leaves no marker, so the file is still the store's truth for the next read and the next write.
- **The rolling backup keeps its one generation ([ADR 0018](0018-rolling-store-backup.md)) and becomes a whole-database copy.** Before a changed write modifies its first page, the database is copied to `tandem.db.bak` through SQLite's backup API, from a second read-only connection — a WAL reader sees the last committed state while the write waits, and the API cannot run against the connection holding the write lock. The copy goes to a same-directory temp and is renamed over the destination, so a failed copy leaves the previous backup untouched; the destination is put back in rollback journal mode, so the one file opens read-only without a `-shm` beside it. A copy that fails fails the write; a read never writes; the home's **first** write has no earlier state to roll, so no `.bak` appears until the second.
- **The sidecar lock is retired, not idle.** The temp + `fsync` + `rename` dance and `tandem.lock` are gone from the store: a transaction is the atomic write, and SQLite's journal covers the kill-mid-write case. No store operation takes a sidecar lock — the comment append is one transaction now, and its existence check rides in it — so a stale `tandem.lock` beside a home is inert, and removing it is housekeeping rather than repair. `doctor`'s `lock` check keeps its name ([ADR 0014](0014-cli-doctor.md)) and its non-destructive probe: it now begins a write transaction on a read-write no-wait connection and rolls it straight back.
- **The corrupt-file incident class is dissolved.** There is no quarantine-and-restart for the ticket domain: a write is one transaction, so the erasure-by-an-older-writer and the half-written file that [ADR 0001](0001-store-protocol.md)'s recovery path existed for cannot happen, and a legacy JSON file that will not decode fails the read loudly with the fix in the message instead of being moved aside and restarted empty. The sidecar domains' legacy files keep their own quarantine until their import lands, and `RecoveryFailure` survives for them; nothing in the ticket path recovers a store into existence.

## Why

- **Counts are the ask, and a file cannot answer them.** Open and done come from `COUNT(*)` without loading the model; tokens, cost, seconds and durations are typed columns, not strings a reader parses. The ticket rows carry `position` for the stored order [ADR 0006](0006-stored-order-and-sections.md) made the list's meaning, and the schema can be asked about a ticket without decoding a whole envelope.
- **A transaction replaces four failure modes with none.** The lock's 2 s retry, the temp file, the fsync and the rename were each a place to be half-done; a killed write now rolls back, and the next read sees the previous state. The one thing the old protocol could not do — a compound write that is all or nothing — is what a comment append needs, and it is free.
- **A marker, because "is this the store?" is a question about history.** The database's existence answers "has a build reached this home", not "did the import finish". Only a durable row written with the rows answers the second, and it answers it for a reader as well as a writer — which is what keeps a first read from lying.
- **The JSON reader stays, because the file stays.** The import copies the file aside and leaves the original where it is: it is the evidence the import is true, and a human who restores a copy is making a claim the reader should answer. Reading both names and both shapes costs one struct and one decode that are already tested.
- **The `.bak` stays a copy, not a link, and now a whole database.** A hard link would share an inode with a file the old protocol invited humans to edit in place; the backup API gives one complete generation atomically, which is what the `mv` recovery story always claimed.

## Where this lands

- **P2** (`396287D4`, PR #187): the comments, sessions, sprints and settings domains re-backed on the same database, each importing its own JSON file once on its own first write, and the `RecoveryFailure` note kept for the legacy files that still quarantine themselves.

## Amendments to earlier records

- **[ADR 0001](0001-store-protocol.md), 2026-10-26.** The store is no longer a single JSON file read and written by several processes through a sidecar `flock`; it is `tandem.db`. The envelope, the atomic-rename dance, `tandem.lock` and the quarantine-and-restart are retired for the store. What survives from 0001: a reader never writes, a reader always sees a consistent state, contention is bounded and surfaces as a loud "locked" error, and the home rule (a dev build gets `~/.tandem-dev`) is untouched.
- **[ADR 0018](0018-rolling-store-backup.md), 2026-10-26.** The rolling backup is now `tandem.db.bak`, one **whole-database** generation taken through SQLite's backup API before the write's first page change; that record's examples spell the file `todos.json.bak`, which is the name it had when it was written, and the clause "under the same sidecar `flock`" now reads "inside the write's transaction, before it modifies the database". The one-generation rule, the take-it-before-the-write seam, the "a copy we cannot take fails the write" rule and the "no restore verb, `mv` is the restore" rule are unchanged.
- **[ADR 0006](0006-stored-order-and-sections.md), 2026-10-26.** The envelope's `version` is no longer the migration seam — `schema_migrations` is — and "the file stays legible by hand" no longer describes the store. The decision itself stands in the rows: `tickets.position` **is** the list order, never derived from `createdAt`; lanes are `lanes.position` plus a nullable `lane` on the ticket; the array stays grouped by lane, default first. The additive-fields-keep-the-version rule has no successor because the version it protected is gone.
- **[ADR 0014](0014-cli-doctor.md), 2026-10-26.** The check list is **seven**: `home`, `store`, `bikeshed`, `comments`, `lock`, `app`, `skills`. `comments` joined with [ADR 0017](0017-the-ticket-model.md)'s comment log and can fail — a log that is present but unreadable is a failure; `lock` no longer probes a flock but a write transaction, under the same name and the same non-destructive rule. The `store` row now reads `tandem.db — v<n>; <open> open, <done> done; <backup>`, with a `; a JSON store file is also present … — a fork` clause when a legacy file sits beside an imported database. Four checks can fail — `store`, `bikeshed`, `comments`, `lock`.
- **[ADR 0017](0017-the-ticket-model.md)'s comments amendment, 2026-10-26.** The discussion log is the `comments` table, not `<home>/comments/<ticket-id>.jsonl`, and an append is one transaction with no sidecar flock. The legacy logs are read as the fallback until the comments domain's first write imports them once, each copied aside as `<name>.pre-sqlite-<unix-ts>`.
- **[ADR 0027](0027-session-records.md), 2026-10-26.** A session is still a record and never a ticket, and its fields and verbs are unchanged; it is stored in the `sessions` table rather than `sessions.json`, and its own `sessions.lock` goes with the file.
- **The settings docstring's amendment.** The old reason for a separate file — "deliberately separate from the store schema" — died with the one-database decision. A setting is a `settings` row; adding one is one more `key`/`value` row, never a migration. `settings.json` is the read-fallback and the one-time import's source.

## Decided against

- **A database per domain** — the question the ask started from ("counts") spans domains, and each file would need its own marker, its own backup and its own connection policy. One file, one `.bak`, one seam.
- **Keeping `tandem.lock` beside the database** — a lock over a file that already serialises its writers is a second, weaker truth. It would also invite "which one is the lock?" in exactly the recovery moment a human is reading the directory.
- **Table emptiness as the import signal** — answered above: a killed first write and a genuinely empty home are the same rows, and one of them must not hide a full JSON file.
- **A package (GRDB, SQLite.swift) or an ORM** — the system `libsqlite3` ships wherever the core can run; the wrapper is mechanics only (open, statements, transactions, the busy timeout, the backup API) and the migrations are about fifty lines. A dependency would own the seam the ADR is about.
- **JSON blobs in a `records` table** — it buys schema-free storage at the price of the query the ask was made for. Typed columns, except the small ordered lists never filtered on (a sprint's batch and runs, a settings roster), which stay JSON text.
- **Deleting the JSON file after the import** — it is the evidence the import is true, and the read-fallback's one-generation-deeper rule needs it to exist. It stays, and it is inert.
- **Rotating backups, a restore verb, a timestamped series** — as in ADR 0018: a backup system, not a store invariant.
- **Rewriting ADR 0001, 0006, 0014, 0017, 0018 or 0027** — they say what was decided then, and each carries a dated pointer here; the amendments above hold the text, in one home.

## Consequences

- **The public surface did not move.** `Store`'s operations, the CLI's output shapes and the app's faces are the same types over the same model; the storage beneath them changed. `Store.health()`, `backupHealth()`, `schemaVersion()`, `lockIsHeld()` and `hasImportedTickets()` are the read-only diagnostics `doctor` reads (ADR 0014), none of them writing or importing.
- **What a fresh home holds after its first write:** `~/.tandem/tandem.db`, the WAL's `tandem.db-wal` and `tandem.db-shm` while a connection is open, and the bikeshed folder. `tandem.db.bak` appears with the second changed write; a legacy `tickets.json` (or `todos.json`) sits beside them as `tickets.json.pre-sqlite-<ts>` — the copy — with the original still in place, never read again.
- **A hand-restored JSON file beside a database that already imported is ignored.** This is the marker's cost, stated plainly: the marker says the domain was imported, so the file is not read, and `doctor` calls it a fork. Copying a backup file back is **not** a recovery path. The recovery paths are `tandem.db.bak` — remove the journal files and the database, then move the backup over it, so a clean close's already-absent `-wal`/`-shm` cannot block the restore: `rm -f ~/.tandem/tandem.db-wal ~/.tandem/tandem.db-shm ~/.tandem/tandem.db` then `mv ~/.tandem/tandem.db.bak ~/.tandem/tandem.db` — or, deliberately and for one domain, dropping its `store_imports` row so the next write imports the file again. A file copied back *and* a marker left in place is a fork, and the database wins. **The same marker silences an older build:** a pre-v0.27.0 writer that still rewrites `tickets.json` beside the database is writing where nothing reads, so every writer of a home — the app, the bundled CLI, an older copy run from a shell — has to be upgraded together.
- **`doctor`'s fork line fires for as long as the file exists.** The clause "a JSON store file is also present at … — a fork, ignored since the database took over" is true every time it is read, because nothing deletes the file. It is a statement, not a warning that clears; a human who wants it gone removes the file.
- **The whole ticket domain is re-inserted on every write.** `writeContents` deletes `tickets` and `lanes` and inserts them from the model — 439 rows on this Mac, one transaction, a few milliseconds. It is the file's old write-whole semantics kept deliberately: the model is the unit of truth, an incremental diff would be a second place for order and lanes to be computed, and the counts the ask wanted are still index and scan, not row walks. The cost is linear in the board's size and is paid once per write, not per read.
- **Every changed write copies the whole database.** `tandem.db.bak` is a ~2 MB copy on this Mac's board, before each write; it is the price of one complete previous generation, and it is why the backup, not a WAL segment, is the restore story.
- **The residual, unowned here:** the sidecar domains keep their own legacy quarantine until each imports; a diagnostics read of a home mid-import reports the JSON's counts under the database's path; and the source docstrings still speak of the JSON files in places (the review of `FD0DE150` listed them). None changes a decision; each is a ticket, not a drive-by edit in a prose PR.
