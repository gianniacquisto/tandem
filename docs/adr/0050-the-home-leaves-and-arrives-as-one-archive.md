# The home leaves and arrives as one archive

> **Status:** In force. See [the index](README.md).

A Tandem home is two things, `tandem.db` and `bikeshed/`, and until now there was no supported way to move one: [ADR 0018](0018-rolling-store-backup.md)'s rolling backup is one write old and covers no notes, and a user changing machines, a self-hoster leaving or a hosted workspace changing region copied files by hand. [ADR 0048](0048-hosted-tandem-is-one-serve-per-workspace.md) promises that a workspace leaves, arrives or changes region as one archive, and that a suspended workspace still yields its export while its instance is stopped. The fleet runs the published release unpatched, so the verb is an open core feature a self-hoster gets too.

Decided 2026-11-17 (CUT-35, refined 2026-11-16; the board's download is CUT-38).

## Decision

- **One `.tar.gz`, written as a stream.** `tandem export --out <path|->` writes entries in this order: `tandem.db`, every regular file under `bikeshed/` by its vault-relative path, and `manifest.json` last. The manifest holds the archive format version (1), the store's schema version, the tandem version, the creation time and, for every other entry, its path, size and SHA-256. It is last because the digests are computed while the bytes stream, so a cut archive has no manifest and is refused as damaged. Never archived: `tandem.db.bak`, lock files, temp files, WAL and journal files, symlinks (the rule of COR-14). Zip was rejected: its directory sits at the end and wants a seekable output, while tar.gz streams from the first byte and opens with stock tools on macOS, Linux and current Windows.
- **What "consistent" means.** The store is one committed instant, taken through SQLite's backup API into a temp copy beside the home (the rolling backup's own copy path, a second, on-demand copy of the store with its own text here: ADR 0018's "no restore verb" stands for the rolling `.bak` and is untouched). Each note is whole, because note writes are atomic renames and each file is opened once and read from that handle. No lock is held across the walk. The store and the notes are two nearby instants, not one transaction: a note edited by hand in another program during an export may be caught either side of the edit. The export is not a backup schedule and moves no revision.
- **Secrets stay out.** The archive carries the board and the notes and, once CUT-36 lands, member names and roles. It carries no browser session, no token and no token digest. In `rust/core/src/store/export.rs` every table of the schema is classified `carried` or `emptied` in one list, and the export fails closed on a table that is in neither; a test fails the build until a new table is placed. The copy, never the live store, has its emptied tables emptied, is vacuumed and is left in `journal_mode=DELETE`, so no emptied row survives in a free page and no WAL travels. Today no table is emptied: CUT-34's `browser_sessions` and CUT-36's token table are classified in their own changes. An imported home therefore starts with nobody signed in and no tokens issued. The archive is not encrypted (human decision, 2026-11-16): keeping the file safe is its owner's job.
- **One permission check.** `archive::may_export` takes the caller's principal (how it reached the home, and the resolved actor) and decides; the CLI verb and CUT-38's route call it and nothing else does. It allows every principal that exists today (the operator at the home, loopback, `--allow-unauthenticated`, the token holder), because no members exist and whoever reaches the home is its owner, and it fails closed on a principal it does not know. CUT-36 binds it to its admin role for team workspaces and leaves the solo owner free. **What it stops:** the one-step bulk export by a member who is not an admin. **What it does not stop:** a member who can read every ticket and note from copying them one by one, and the offline CLI, where whoever can read the home's files could copy them anyway; file permissions are that boundary, and `X-Tandem-Agent` stays attribution, never the principal (ADR 0047).
- **The export record.** One core function writes one line per export that starts: the actor, the time and the door (`cli` or `board`), never a token, a path or content. It is a `tracing::info!` event, and the CLI verb, which installs no subscriber, prints the same line to stderr. There is no store row: a row would change the store being exported, make a read-only verb write and move the revision. A durable, in-board audit trail is CUT-36's.
- **Import goes into an empty home, and nothing else.** `tandem import <path|-> [--max-bytes <n>]` refuses a home that has a `tandem.db`, a `tandem.db.bak`, a WAL or journal file, or any entry under `bikeshed/`; a lock file alone does not refuse. There is no merge and no force flag (human decision). The archive unpacks into a private temp directory inside the home's own directory (0700, files 0600, same volume) and nothing enters the home until everything has passed: only regular files and directories; no absolute path, no `..`, empty or `.` component, no backslash; only `manifest.json`, `tandem.db` and paths under `bikeshed/`; no duplicate; the byte ceiling enforced while streaming; the manifest present, its format known, and every entry matching its listed size and digest with none unlisted or missing; then the unpacked store opened read-only, where the integrity check passes, `schema::refuse_legacy` run against the file itself (not the manifest's claim) refuses a newer or foreign schema, no trigger, view or table the schema does not define exists, and every emptied table is empty. Then two renames inside the home, `bikeshed/` first and `tandem.db` last, so the store's arrival is the commit. A crash between them leaves notes and no store, which the next import refuses by name as non-empty; `docs/store.md` says to remove that `bikeshed/` and run again. Any refusal removes the temp directory and leaves the home as it was. An archive from an older schema imports as it is and migrates on the first write, through the path that rolls the backup first. There is no import over HTTP and no upload in the board (human decision); a hosted customer moving in uploads on the hosted account page and the service runs this verb.
- **No remote form, no tool.** Both verbs open the home directly and refuse by name under `TANDEM_SERVER`. Neither is an MCP tool: an agent has no need to move a workspace, and a remote user downloads from the board (CUT-38). The limits are the hosted side's (HOS-9): the core offers `--max-bytes` and enforces the manifest's sizes, and fixes no ceiling of its own.
- **Layering.** `rust/core/src/archive.rs` owns the format, the export, the import, `may_export` and the record; SQL stays in `rust/core/src/store/` (ADR 0009); the CLI holds argument parsing and wording. Two crates join the build, `tar` and `flate2`, for the reasons given in `rust/Cargo.toml`.

## Amends

[ADR 0047](0047-serve-is-the-single-door.md), the line "A verb with no tool (`serve`, `note rename`, `note stats`, `ticket set --append-description`) refuses in remote mode by name", gains `export` and `import`: both open the home directly and refuse in remote mode by name.

[ADR 0018](0018-rolling-store-backup.md) is not amended. Its "no restore verb" stands for the rolling `.bak`; the export is a second copy of the store, taken on demand and carried with the notes, not a backup generation.
