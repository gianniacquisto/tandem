# Releasing

Two repos: the main repo holds the source; [`gianniacquisto/homebrew-tap`](https://github.com/gianniacquisto/homebrew-tap) holds the [Homebrew cask](https://github.com/gianniacquisto/homebrew-tap/blob/main/Casks/tandem.rb) that installs the prebuilt app. brew only reads taps from its fixed tap directory, so on any dev machine the working copy is wherever brew keeps the clone — `brew tap gianniacquisto/tap` creates it at `$(brew --prefix)/Library/Taps/gianniacquisto/homebrew-tap`. That directory is an ordinary git clone of the tap repo: branch, commit, and push from there (`brew update` keeps it current).

To cut a release:

1. Cut the release on the integration branch, then move the release line to it by PR (three acts):
   - Tag the `dev` head and push the tag — a lightweight tag, the repo's convention; an annotated tag breaks a branch-ref push: `git tag v0.21.0 dev && git push origin v0.21.0`.
   - Watch the [Release workflow](https://github.com/gianniacquisto/tandem/blob/dev/.github/workflows/release.yml) run for the tag (step 2) until the GitHub release publishes.
   - Open the dev→main release PR (title `Release vX.Y.Z`) and merge it once its `release` check is green. No fresh wait is needed: the PR's head is the tagged commit, so the tag run's green check already attests it — v0.21.0's release PR (#142) was created and merged within seconds. The raw push (`git push origin vX dev:main`) is gone: `main` is branch-protected, so it fails with GH006, and once a release-merge sits on `main` a later `dev:main` push would be non-fast-forward anyway. The merge leaves `main`'s head one release-merge past the tag, its tree identical to the tag's ([ADR 0019](adr/0019-integration-branch.md)).
2. The [Release workflow](https://github.com/gianniacquisto/tandem/blob/dev/.github/workflows/release.yml) is three jobs. `test` runs the package test suite, the README grammar gate (`Scripts/check-readme-grammar.sh` — the README's CLI block against `Usage.swift`) and the editor-bundle gate; `build` builds and verifies the artifact and uploads it; the two run in parallel, each on its own runner. The third job, `release`, waits for both and then publishes the GitHub release for the tag with `Tandem-<version>.zip` and `SHA256SUMS` attached — it publishes only when both halves are green, so a release is never cut from a run whose tests failed. That job is named `release` because `dev` and `main` require a status check by that name; renaming it would leave the branch protection waiting for a check that never reports, so the split keeps the name and the protection untouched. The workflow also runs on pull requests — the same two halves, never publishing — so a release can be dry-run on a PR. Re-pushing the same tag re-cuts the release. The release body carries what shipped (7B005267, BCE67BAE): `Scripts/release-notes.sh` writes it — the fixed install line as the lead, then the PRs merged on `dev` since the previous tag (`git log <prev>..<new> --first-parent --merges`, PR titles and labels looked up via `gh`, falling back to the merge subject's branch area when the lookup fails or when the words place nothing), grouped by kind in a fixed order: `## Features`, `## Bugs and fixes`, `## Docs and infra`, and `## Other (unclassified)` for a PR whose labels, title and branch area all say nothing — the explicit fallback, never a guess, so a mis-grouped PR wants a label. The kind comes from the PR's labels first, then the words of its title, then the branch area (the lists are in the script's header); empty sections are omitted. The tag run's `release` job generates it at publish time, so no release act carries a hand-written body; the previous tag must be present in the checkout, which is why that job checks out with `fetch-depth: 0`.
3. File the wiki note — the same content, into the bikeshed: `Scripts/release-notes.sh vX.Y.Z --capture` from a checkout that has the tags. It files one capture through `tandem-cli note capture --kind fact --project tandem --session release-notes`, so the note lands in the hidden saddlebag at `projects/tandem/.raw/release-notes/<utc>-fact-release-<version>-what-shipped.md`; the next consolidation pass promotes it into the curated `Releases` note (the pass is the curated layer's only writer, so the script never writes there itself). The curated note is **one `Releases` page with one section per tag** (`BCE67BAE`'s shape decision, settled by the review of PR #184): a new release appends its section, it does not file a note of its own. The capture's shape is one `# Release <version>: what shipped` title, the install lead line, then the same kind sections as the body. Retrofitting a release is the same call — v0.25.0 was filed that way. It is a local step on purpose: the CI runner has no bikeshed, so the workflow never passes `--capture`.
4. The tap's `brew bump` workflow never fires on a release: its triggers are a daily 06:55 UTC cron and a push to `autobump.yml` itself — no `workflow_dispatch`, no release trigger — and when it runs it passes `secrets.GITHUB_TOKEN`. It is background upkeep at most; every recent release was bumped by hand (tap PRs #16–#20).
5. Bumping by hand is the actual release act: bump the cask to the new version with the artifact's real sha256, and verify before pushing: `brew style Casks/tandem.rb && brew audit --cask --strict gianniacquisto/tap/tandem`.
6. Users get it with `brew update && brew upgrade --cask gianniacquisto/tap/tandem`.

Always spell the tap's cask out in full. The token is `tandem`, which collides with Homebrew's unrelated `tandem` (tandem.chat, 348 MB); the Caskroom is keyed by token, so a bare `brew upgrade --cask tandem` resolves core's cask against this tap's files and installs *that* app over this one — and `brew outdated --cask` offers its version as an upgrade forever. Renaming the token is the only real fix; until then, every user-facing command carries the tap prefix (installing with `brew install --cask gianniacquisto/tap/tandem` from the README is safe).
