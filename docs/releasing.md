# Releasing

Two repos: the main repo holds the source; [`gianniacquisto/homebrew-tap`](https://github.com/gianniacquisto/homebrew-tap) holds the [Homebrew cask](https://github.com/gianniacquisto/homebrew-tap/blob/main/Casks/tandem.rb) that installs the prebuilt app. brew only reads taps from its fixed tap directory, so on any developer machine the working copy is wherever brew keeps the clone: `brew tap gianniacquisto/tap` creates it at `$(brew --prefix)/Library/Taps/gianniacquisto/homebrew-tap`. That directory is an ordinary git clone of the tap repo: branch, commit, and push from there (`brew update` keeps it current).

The sprint close cuts this tag for the batch it landed: the release step in [`skills/tandem-sprint/SKILL.md`](../skills/tandem-sprint/SKILL.md) §7 runs the acts below, so the sprint that lands the work is the pass that ships it.

To cut a release:

1. Tag the trunk: `main`'s head is the release.
   - Tag `main`'s head and push the tag, a lightweight tag, the repo's convention: `git tag v0.33.0 origin/main && git push origin v0.33.0`. There is no release line to move, because `main` takes the merges, so the tag names the commit that is actually on `main` ([ADR 0019](adr/0019-integration-branch.md)).
   - Watch the [Release workflow](https://github.com/gianniacquisto/tandem/blob/main/.github/workflows/release.yml) run for the tag (step 2) until the GitHub release publishes. The tag run is the release: nothing waits on a PR, and a merge that lands on `main` after the tag ships in the next one.
2. The [Release workflow](https://github.com/gianniacquisto/tandem/blob/main/.github/workflows/release.yml) is three jobs. `test` runs the package test suite, the README grammar gate (`Scripts/check-readme-grammar.sh`, the README's CLI block against `Usage.swift`) and the editor-bundle gate; `build` builds and verifies the artifact and uploads it; the two run in parallel, each on its own runner. The third job, `release`, waits for both and then publishes the GitHub release for the tag with `Tandem-<version>.zip` and `SHA256SUMS` attached; it publishes only when both halves are green, so a release is never cut from a run whose tests failed. That job is named `release` because `main` requires a status check by that name; renaming it would leave the branch protection waiting for a check that never reports, so the name stays and the protection is untouched. The workflow also runs on pull requests, the same two halves, never publishing, so a release can be dry-run on a PR. Re-pushing the same tag re-cuts the release. The release body carries what shipped (7B005267, BCE67BAE): `Scripts/release-notes.sh` writes it: the fixed install line as the lead, then the PRs merged on `main` since the previous tag (the range is `<prevTip>..<newTip> --first-parent --merges`: each tag resolves to the integration tip it names, the second parent when the tag sits on a release merge and the tag itself when it names a commit directly (the tags cut before the trunk flip), so a release tagged either way reads the same PRs; PR titles and labels looked up via `gh`, falling back to the merge subject's branch area when the lookup fails or when the words place nothing), grouped by kind in a fixed order: `## Features`, `## Bugs and fixes`, `## Docs and infra`, and `## Other (unclassified)` for a PR whose labels, title and branch area all say nothing, the explicit fallback, never a guess, so a mis-grouped PR wants a label. The kind comes from the PR's labels first, then the words of its title, then the branch area (the lists are in the script's header); empty sections are omitted. The tag run's `release` job generates it at publish time, so no release act carries a hand-written body; the previous tag must be present in the checkout, which is why that job checks out with `fetch-depth: 0`.
3. File the wiki note — the same content, into the bikeshed: `Scripts/release-notes.sh vX.Y.Z --capture` from a checkout that has the tags. It files one capture through `tandem-cli note capture --kind fact --project tandem --session release-notes`, so the note lands in the hidden saddlebag at `projects/tandem/.raw/release-notes/<utc>-fact-release-<version>-what-shipped.md`; the next consolidation pass promotes it into the curated `Releases` note (the pass is the curated layer's only writer, so the script never writes there itself). The curated note is **one `Releases` page with one section per tag** (`BCE67BAE`'s shape decision, settled by the review of PR #184): a new release appends its section, it does not file a note of its own. The capture's shape is one `# Release <version>: what shipped` title, the install lead line, then the same kind sections as the body. Retrofitting a release is the same call — v0.25.0 was filed that way. It is a local step on purpose: the CI runner has no bikeshed, so the workflow never passes `--capture`.
4. The tap's `brew bump` workflow never fires on a release: its triggers are a daily 06:55 UTC cron and a push to `autobump.yml` itself — no `workflow_dispatch`, no release trigger — and when it runs it passes `secrets.GITHUB_TOKEN`. It is background upkeep at most; every recent release was bumped by hand (tap PRs #16–#20).
5. Bumping by hand is the actual release act: bump the cask to the new version with the artifact's real sha256, and verify before pushing: `brew style Casks/tandem.rb && brew audit --cask --strict gianniacquisto/tap/tandem`.
6. Users get it with `brew update && brew upgrade --cask gianniacquisto/tap/tandem`.

Always spell the tap's cask out in full. The token is `tandem`, which collides with Homebrew's unrelated `tandem` (tandem.chat, 348 MB); the Caskroom is keyed by token, so a bare `brew upgrade --cask tandem` resolves core's cask against this tap's files and installs *that* app over this one — and `brew outdated --cask` offers its version as an upgrade forever. Renaming the token is the only real fix; until then, every user-facing command carries the tap prefix (installing with `brew install --cask gianniacquisto/tap/tandem` from the README is safe).
