# Releasing

One repo, one workflow: a tag's Release run builds and verifies five standalone `tandem` archives, then publishes them with `install.sh` and one `SHA256SUMS`. There is no Homebrew tap, no Electron package and no Node toolchain in the path (CUT-16, [ADR 0046](adr/0046-tandem-serve-and-single-binary-distribution.md)).

A release cuts only on the human's explicit words naming the version: a batch close cuts no release by default and never prompts for one. The manual acts below live in [`examples/skills/tandem-sprint/SKILL.md`](../examples/skills/tandem-sprint/SKILL.md) under Release as the same steps, run by hand when the human asks.

To cut a release:

1. Tag the trunk: `main`'s head is the release.
   - Tag `main`'s head and push the tag, a lightweight tag, the repo's convention: `git tag v2.5.0 origin/main && git push origin v2.5.0`. There is no release line to move, because `main` takes the merges, so the tag names the commit that is actually on `main` ([ADR 0019](adr/0019-integration-branch.md)).
   - Watch the [Release workflow](https://github.com/gianniacquisto/tandem/blob/main/.github/workflows/release.yml) run for the tag until the GitHub release publishes.
   - Pin the Claude Code plugin to the tag: `Scripts/pin-plugin.sh 2.5.0` rewrites the plugin's `ref` in `.claude-plugin/marketplace.json`, after checking the tag is on origin. Land that change on `main` through a PR. Claude Code reads the marketplace from `main` and fetches the plugin from the tag, so the order is tag first, pin second: a ref naming a tag not yet pushed breaks every install ([ADR 0051](adr/0051-a-claude-code-plugin-is-the-connector.md)).
2. The Release workflow is four jobs, all cargo. one `build` matrix job builds five archives: darwin-arm64 (`macos-latest`), darwin-x86_64 (cross-built on the same arm64 runner for `x86_64-apple-darwin`; its smoke runs under Rosetta when `arch -x86_64 /usr/bin/true` succeeds, else `--version` only, and the log says which), linux-x86_64 (`x86_64-unknown-linux-musl`), linux-arm64 (`aarch64-unknown-linux-musl` on `ubuntu-24.04-arm`) and windows-x86_64. The Linux builds are static musl and the job fails if `ldd` reports a dynamic executable. Each runs `cargo build --release -p tandem` with `TANDEM_VERSION` set to the version, package the one executable, and smoke-test it: `tandem --version` names the stamp, `tandem serve --port 0` answers `GET /` and `GET /notes` with `200 OK` and the server's `Content-Security-Policy` header, and the server shuts down cleanly. The archives are `tandem-<version>-darwin-arm64.tar.gz`, `-darwin-x86_64.tar.gz`, `-linux-x86_64.tar.gz`, `-linux-arm64.tar.gz` and `tandem-<version>-windows-x86_64.zip`, each carrying the executable, `LICENSE` and `NOTICE.txt` at its root; the packaging step fails when its listing lacks one.
   - `release` waits for all five. It downloads the archives, runs `Scripts/stage-release-assets.sh <version> dist` to stamp `install.sh` with the tag's version and write one `SHA256SUMS` covering the five archives and the script, verifies the manifest with `sha256sum -c` (or `shasum -a 256 -c`), and on a tag run publishes the GitHub release with those five assets. A re-push of the same tag re-cuts the release without ever removing it: `gh release create` when absent, else `gh release upload --clobber` and `gh release edit`, so `releases/latest/download/install.sh` never 404s mid-run. Before publishing, `actions/attest-build-provenance` signs a provenance attestation for the five archives (the job alone holds `id-token: write` and `attestations: write`); `SHA256SUMS` is kept.
   - The job is named `release` because `main` requires a status check by that name; renaming it would leave the branch protection waiting for a check that never reports, so the name stays and the protection is untouched. Pull-request runs build and verify the same five archives and never publish, so a packaging change is a red check on the PR instead of a broken tag.
3. Users install with the one-liner in [`README.md`](../README.md) (`curl -fsSL .../releases/latest/download/install.sh | sh`), or with the archive for their platform. [`install-paths.md`](install-paths.md) describes what each route asks of the user and how it verifies the download.

**Breaking changes.** A PR that renames or removes an MCP tool, one of its parameters or answer fields, a CLI verb, flag, output field or exit code, an environment variable, or one of the HTTP routes `/health`, `/mcp`, `/events` and `/export`, or changes what one of them means, carries the GitHub label `breaking`. `Scripts/release-notes.sh` lists every such PR first, under "Breaking changes", which is what [versions and compatibility](versioning.md) promises users. A CLI or HTTP removal is deprecated, with a warning, for at least one release before it lands.

The installer line is a contract in two places: `README.md` and the release-notes lead in `Scripts/release-notes.sh`. Change one and the other moves in the same commit.

## Supply chain

- **Audit.** The `deny` job in `rust.yml` runs `cargo deny check` (advisories, licences, bans, sources) against `rust/deny.toml` on every PR and push, and weekly on a schedule, so a new advisory against `Cargo.lock` is found without a push. A new unmaintained-crate notice that is only transitive goes into `ignore` in `deny.toml` with a reason; a vulnerability never does without a decision. Run it locally with `cargo install cargo-deny --locked` and `cargo deny check` in `rust/`.
- **Pins.** Every `uses:` in `.github/workflows` names a full commit SHA with the version in a trailing comment (`rust/core/tests/ci_workflows.rs` enforces it). `.github/dependabot.yml` opens one weekly PR per ecosystem (`cargo` in `rust`, and `github-actions`) that moves them.
- **Checkouts** that do not push set `persist-credentials: false`.
