# Research: Editor technology — markdown editing + live preview in SwiftUI

Research report for [ticket 01](../issues/01-editor-technology.md). Date: 2026-10-14.
Method: primary sources only — Apple developer docs and WWDC sessions, package repos and npm release metadata, vendor blog/changelog posts. Claims are cited inline. One measurement (JS bundle size) was taken locally on this machine and is flagged as such.

## Question (from the ticket)

Which editing + rendering technology should the spec mandate for the bikeshed editor — a syntax-highlighted markdown editor with **inline live preview** (Obsidian-style: markdown renders in place as you type) — in SwiftUI on macOS 26+? Split view (source | rendered) is the sanctioned fallback if inline proves infeasible; the research must deliver a feasibility verdict on inline.

## Verdict

**Inline live preview: FEASIBLE.** Obsidian — the reference product for exactly this interaction — runs it on CodeMirror 6 (CM6): its developer docs state "Obsidian uses CodeMirror 6 (CM6) to power the Markdown editor" ([Obsidian docs, Editor extensions](https://docs.obsidian.md/Plugins/Editor/Editor+extensions)), and Obsidian's [2022 migration guide](https://obsidian.md/blog/codemirror-6-migration-guide) documents the move from CM6 v0.19 to v6.0. The mechanism is small and well-documented: an incremental markdown parser ([@lezer/markdown](https://www.npmjs.com/package/@lezer/markdown)) plus CM6 decorations that remove syntax markers from flow — an open-source reference implementation, [Atomic Editor](https://github.com/kenforthewin/atomic-editor), documents it directly: "Active / inactive states toggle token visibility via `Decoration.replace({})`, which removes characters from flow without changing the enclosing line's measured height" (its [`docs/architecture.md`](https://github.com/kenforthewin/atomic-editor/blob/main/docs/architecture.md)).

- **Primary path: WKWebView + CodeMirror 6** — `basicSetup` + [`@codemirror/lang-markdown`](https://www.npmjs.com/package/@codemirror/lang-markdown) (GFM), plus a live-preview decoration extension modeled on Obsidian/Atomic Editor. Bundle into the app's Resources (~597 KB min / 203 KB gzip, measured §2). No web workers required, so `loadFileURL` from the bundle works (unlike Monaco).
- **Fallback: split view** — source pane (CM6 in source mode, or plain `NSTextView`) + rendered pane ([MarkdownUI](https://github.com/gonzalezreal/swift-markdown-ui) or its successor [Textual](https://github.com/gonzalezreal/textual), both MIT; MarkdownUI is now in maintenance mode).
- **Native-only alternative (not primary): TextKit 2 / `NSTextView`** — syntax highlighting in place is easy, but there is **no public hook for hiding syntax markers**: the TextKit 1 `NSLayoutManager` glyph-stripping trick has no TextKit 2 equivalent (Apple: "there are zero glyph APIs in TextKit 2" — [WWDC22 10090](https://developer.apple.com/videos/play/wwdc2022/10090)). A native path therefore can't deliver *true* Obsidian-style hiding (markers gone, rendered in place) without an unsupported research bet; it can deliver "styled source" (markers visible but dimmed/colored, formatting applied), which is a different, weaker feature.

## 1. TextKit 2 / `NSTextView` with custom highlighting

**What TextKit 2 gives us.** `NSTextLayoutManager` is "the primary class that you use to manage text layout and presentation for custom text displays" ([Apple docs](https://developer.apple.com/documentation/appkit/nstextlayoutmanager); introduced macOS 12). Architecture: `NSTextContentStorage` (backed by `NSTextStorage`) → `NSTextElement`s (default `NSTextParagraph`) → `NSTextLayoutFragment`/`NSTextLineFragment` ([WWDC21 "Meet TextKit 2"](https://developer.apple.com/videos/play/wwdc2021/10061)). Since macOS Ventura "all text controls use TextKit 2 by default. Just like UITextView, most NSTextViews get automatic opt in to TextKit 2 and require zero adoption on your part" ([WWDC22 "What's new in TextKit and text views"](https://developer.apple.com/videos/play/wwdc2022/10090)) — so on macOS 26+ a stock `NSTextView` is already TextKit 2, and Apple's current direction is adding extension APIs on top of it (line numbers, collapsible sections, attachment caching — [WWDC26 session 370](https://developer.apple.com/videos/play/wwdc2026/370)).

**How hard is true inline live preview?** The feature has two distinct parts, and only one of them is easy:

1. *Style the markdown in place* (bold is bold, code is monospaced + background, headings larger, blockquote tinted): **easy**. This is just attribute runs on the text storage; re-tokenize on edit and set attributes per range. `swift-markdown` (cmark-gfm AST, §3) or a line-based tokenizer can produce the ranges. No layout-system tricks needed.
2. *Hide the syntax markers* (the `**` of `**bold**` disappears, `#` of a heading disappears — what makes it feel like Obsidian rather than a syntax highlighter): **no public mechanism in TextKit 2**. The established trick is TextKit 1-only: tag characters as invisible in the storage, then strip them in the `NSLayoutManager` delegate hook `layoutManager(_:shouldGenerateGlyphs:properties:characterIndexes:font:forGlyphRange:)` "preventing change to the underlying storage" — and on Apple's own forums the practitioner experience is explicit: "In TextKit 2, I don't see an opportunity to do this" ([Apple Developer Forums, TextKit tag](https://developer.apple.com/forums/tags/textkit)). The reason is architectural, not an oversight: TextKit 2 deliberately removed glyph-level APIs ("The glyph-based APIs on NSLayoutManager assume you can directly associate a contiguous range of characters with a contiguous range of glyphs, and that's just not true for all scripts… that's why there are zero glyph APIs in TextKit 2. You can't just substitute a single TextKit 2 API for a TextKit 1 glyph API." — [WWDC22 10090](https://developer.apple.com/videos/play/wwdc2022/10090)). The remaining TextKit 2 seam is the `NSTextLayoutManager` delegate that swaps in custom `NSTextLayoutFragment`s per element ([WWDC21 10061](https://developer.apple.com/videos/play/wwdc2021/10061)) — element-granular (per paragraph), not per-character, so it can't zero-width individual markers. The other option — maintaining a separate display string with a model↔view offset map — is a custom text engine (caret/selection/undo/IME mapping across two coordinate systems); that is a multi-week research project with no prior art in public Swift code.

**Assessment.** TextKit 2 is the right tool for a *native, styled-source* editor and remains a credible fallback source pane. For *true* inline live preview (markers hidden) it is **infeasible-with-public-APIs** — feasible only via (a) forcing TextKit 1 compatibility mode (`usingTextLayoutManager: false`) to use the glyph-stripping delegate, or (b) the display-string mapping project. Note (a) is a real escape hatch but contradicts the platform direction (TextKit 2 is the default and the path Apple extends — WWDC26 370), and TextKit 1 + heavy custom layout is exactly the legacy surface Apple is de-emphasizing.

## 2. WKWebView + CodeMirror 6 (or Monaco)

### CodeMirror 6 — what Obsidian uses

- **Obsidian's stack, from primary sources.** "Obsidian uses CodeMirror 6 (CM6) to power the Markdown editor" ([Obsidian developer docs](https://docs.obsidian.md/Plugins/Editor/Editor+extensions)); Obsidian's [CodeMirror 6 migration guide (2022-06-14)](https://obsidian.md/blog/codemirror-6-migration-guide) states "CodeMirror 6.0 is finally stable. That means Obsidian will be migrating from CM6 v0.19 to v6.0 soon" — i.e. Obsidian has run CM6-based editing for ~4 years, at exactly our scale and beyond (vaults of thousands of notes).
- **The model.** CM6 state is an immutable `EditorState` (doc + selection + fields); every edit is a `Transaction` ([CM6 Reference Manual](https://codemirror.net/6/docs/ref/)). Documents live in an immutable tree (`Text`) with O(1)-ish structure-sharing updates — a 300 KB note is cheap. Undo/redo, selection, and IME composition are first-class (the `composing` state is tracked per the same manual), which is why "caret, selection, and undo sane" comes for free rather than being hand-built.
- **Highlighting.** `@codemirror/lang-markdown` v6.5.2 ([npm](https://www.npmjs.com/package/@codemirror/lang-markdown); MIT; ~5.1M weekly downloads; published within the last two months) provides `markdown()` with `markdownLanguage` = "Language support for GFM plus subscript, superscript, and emoji syntax", strict-CommonMark `commonmarkLanguage`, `codeLanguages` for fenced code blocks, and a markdown keymap (Enter continues list/quote markup, Backspace deletes markup, `pasteURLAsLink`). Note: the GitHub mirror ([github.com/codemirror/lang-markdown](https://github.com/codemirror/lang-markdown)) was **archived 2026-04-15** — the source moved to [code.haverbeke.berlin](https://code.haverbeke.berlin/codemirror/lang-markdown); npm remains the distribution channel and is actively published (verified via npm metadata).
- **Incremental parsing.** `@lezer/markdown` v1.8.0 ([npm](https://www.npmjs.com/package/@lezer/markdown); MIT; published 2026-10-07) is "an incremental Markdown (CommonMark with support for extension) parser… it produces Lezer-style compact syntax trees and consumes fragments of such trees for its incremental parsing." Ships GFM extensions (Table, TaskList, Strikethrough, Autolink) plus Subscript/Superscript/Emoji. It deliberately trades a little conformance (e.g. doesn't validate link references) for single-pass incremental speed — an acceptable trade for an editor (the *rendered* pane or export path can use a conforming parser like `swift-markdown`).
- **Inline live preview mechanism.** CM6's `Decoration` API: "A decoration provides information on how to draw or style a piece of content" ([CM6 Reference Manual](https://codemirror.net/6/docs/ref/#view.Decoration)), supplied through the `EditorView.decorations` facet (per Obsidian's [migration guide](https://obsidian.md/blog/codemirror-6-migration-guide): "providing decorations from a view plugin now happens by providing a function to the `EditorView.decorations` facet"). Hiding markers = `Decoration.replace({})` over the marker ranges: "removes characters from flow without changing the enclosing line's measured height" (Atomic Editor [`docs/architecture.md`](https://github.com/kenforthewin/atomic-editor/blob/main/docs/architecture.md)). Two invariants from that architecture doc worth copying into the spec: (1) **raw markdown is the source of truth** — decorations are view-only; (2) line heights must depend on CSS classes, not on whether tokens are visible, to avoid layout shift as markers appear/disappear. The same doc frames the tradeoff honestly: "CM6 is a text editor at heart — 'WYSIWYG' in CM6 means carefully choreographed decorations layered over a raw text buffer, not a rich-content model like ProseMirror's."
- **Prior art for the extension we'd write.** [Atomic Editor](https://github.com/kenforthewin/atomic-editor) — "CodeMirror 6 markdown editor with Obsidian-style inline live preview", open source, with a React shell + an imperative API and a documented architecture (decoration engine as a `ViewPlugin`, block widgets for tables/images). It is a reference implementation, not a required dependency. (Also exists: [tiagosimoes/codemirror-markdown-hybrid](https://github.com/tiagosimoes/codemirror-markdown-hybrid), a lighter "preview unfocused lines" variant — relevant if the spec later wants a compromise mode.)
- **Packaging size (measured on this machine, 2026-10-14; Node v26.11.1, esbuild).** Minimal bundle of `basicSetup` (codemirror 6.0.2) + `markdown()` (lang-markdown 6.5.2, state 6.7.6, view 6.43.14, language 6.13.1, @lezer/markdown 1.8.0): **611,701 bytes minified (≈597 KiB), 208,073 bytes min+gzip (≈203 KiB)**; largest chunks `@codemirror/view` 483 KB, `@codemirror/state` 144 KB, `@codemirror/language` 95 KB, `@lezer/markdown` 85 KB (source sizes pre-minify). This lands in app Resources and is negligible against the app binary; it is fetched/loaded once from the local bundle.
- **Native feel.** `WKWebView` is a regular `NSView`; embedded via `NSViewRepresentable`, with a transparent background and the system font it is indistinguishable from native chrome. WebKit applies macOS text services (spell check, text replacement) to the editable DOM; CM6's own keymap handles macOS standard shortcuts (undo/redo, word selection). Accessibility: CM6 has a documented accessibility model (announcements, DOM structure) — the webview bridge is one hop from the AX tree, a known trade rather than a blocker. The residual "non-native" surface is: one extra process (WebKit content process, standard memory footprint) and any behavior that must cross the JS boundary (file ops, links) needs explicit bridging (below).

### Monaco — evaluated, rejected for this use case

[Monaco](https://github.com/microsoft/monaco-editor) ("the fully featured code editor from VS Code", MIT, 46.9k stars) is a *code* editor: markdown gets syntax highlighting (Monarch grammar), no live-preview capability — and its own README FAQ documents a hard constraint for our embedding model: "HTML5 does not allow pages loaded on `file://` to create web workers. Please load the editor with a web server on `http://` or `https://` schemes." Embedding Monaco in a bundled-file WKWebView therefore means standing up a local HTTP server for the editor — real complexity for a feature CM6 doesn't need. Its size is also an order of magnitude larger (VS Code's editor surface, workers included). Not the tool for a notes editor.

**Read of the landscape.** No credible Swift package does *editing with inline live preview* — which matches the verdict: that capability is owned by the web-editor ecosystem (CM6), and the Swift ecosystem splits cleanly into (a) editors that highlight (CodeEditSourceEditor — and it self-declares not production-ready), (b) renderers (MarkdownUI/Textual), and (c) parsers (swift-markdown/cmark-gfm). The composition that follows is: CM6 in a WKWebView for the editor (primary), swift-markdown in-process for indexing (wikilinks/backlinks/search — it's Apache-2.0, thread-safe, and the same GFM dialect CM6 highlights, so source and index agree), and MarkdownUI or Textual only if the split-view fallback is taken (Textual is the forward-looking pick; MarkdownUI is the battle-tested-but-frozen pick).

## 4. Folder watching (FSEvents)

**What we have today.** `Sources/Tandem/StoreWatcher.swift` watches one directory with a `DispatchSourceFileSystemObject` on the directory fd (`O_EVTONLY`, mask `.write, .rename, .delete`, handler on the main queue). It answers "did *the directory* change" — correct for the todos store because the store writes atomically (`.tmp` + `rename`, verified per the file's doc comment), so the directory-level event is the whole story. It gives **no file-level information** (which note changed, whether it's a file or folder) and is per-descriptor: a tree of notes would need one monitor per subdirectory, with bookkeeping as folders appear/disappear — and even then, each event still means "rescan this directory."

**What a vault needs.** One stream over the whole hierarchy, with per-file paths. That is exactly what FSEvents provides:

- `FSEventStreamCreate(allocator:callback:context:pathsToWatch:sinceWhen:latency:flags:)` ([Apple docs](https://developer.apple.com/documentation/coreservices/1443980-fseventstreamcreate); macOS 10.5+). `pathsToWatch` is "a CFArray of CFStringRefs, each specifying a path to a directory, signifying **the root of a filesystem hierarchy** to be watched for modifications" — i.e. recursive by construction; nested folders (sanctioned by the map) cost nothing. "In order to start receiving callbacks you must also call `FSEventStreamScheduleWithRunLoop()` and `FSEventStreamStart()`" (schedule-on-a-dispatch-queue is the modern variant).
- `sinceWhen = kFSEventStreamEventIdSinceNow` (documented on the same page).
- `latency`: "The number of seconds the service should wait after hearing about an event from the kernel before passing it along… Specifying a larger value may result in more effective temporal coalescing, resulting in fewer callbacks and greater overall efficiency." — this is the built-in debounce; ~0.2 s is a reasonable spec value (atomic note writes produce a `.tmp`-write + rename pair that coalesce into one batch).
- Flags ([FSEventStreamCreateFlags](https://developer.apple.com/documentation/coreservices/fseventstreamcreateflags)):
  - `kFSEventStreamCreateFlagFileEvents` ([docs](https://developer.apple.com/documentation/coreservices/kfseventstreamcreateflagfileevents)): "Request file-level notifications… instead of only receiving directory level notifications. **Use this flag with care as it will generate significantly more events than without it.**" — at hundreds of notes this volume is trivial, and it's the flag that makes the stream useful for a tree.
  - `kFSEventStreamCreateFlagNoDefer`: deliver file-level events for a file even when its parent directory also changed (needed so an in-place note edit isn't swallowed by a directory event).
  - `kFSEventStreamCreateFlagUseCFTypes`: callback hands you `CFArray`/`CFString` paths + `UInt8` event-flag array — cheap to consume on the callback's dispatch queue.
  - `kFSEventStreamCreateFlagWatchRoot` + the event flag `kFSEventStreamEventFlagRootChanged` ([docs](https://developer.apple.com/documentation/coreservices/kfseventstreameventflagrootchanged)): "a special event sent when there is a change to one of the directories along the path to one of the directories you asked to watch… The path may no longer exist because it or one of its parents was deleted or renamed." — the spec must treat this (and any first batch after a gap) as **full rescan**: it's the missed-events safety net (e.g. vault renamed/moved, app suspended, stream interrupted).
  - Event flags on file paths (e.g. `kFSEventStreamEventFlagItemIsFile`, `…ItemRenamed`, `…ItemRemoved`, `…ItemCreated`) let the handler distinguish "note changed" from "folder renamed" without guessing.

**How the spec should describe it.** *One* `FSEventStream` on `~/.tandem/bikeshed/` (the vault root), `FileEvents | NoDefer | UseCFTypes | WatchRoot`, `sinceWhen = kFSEventStreamEventIdSinceNow`, latency ≈ 0.2 s, scheduled on a background dispatch queue; `StoreWatcher` stays as-is for the todos store (different lifecycle, different granularity, no reason to perturb it). Behavior contract:
1. **Debounce/coalesce** the latency-batched callback into a single "vault changed" pass on the main actor (rebuild tree from the event's paths; reload the open note only if its path is in the batch).
2. **Dedup self-writes**: the app's own saves fire events. Track the app's last write (path + mtime/hash, or a per-file dirty flag) and skip the reload when the event matches the app's own write — otherwise the editor receives its own change as an "external" change.
3. **External change to the open note** while the buffer is dirty → conflict policy (spec decision; simplest sane default: keep the user's buffer, mark the note "changed on disk," offer reload).
4. **Rescan** the whole vault on `RootChanged`, on stream start, and on app launch (FSEvents delivers only changes since the stream started — cold start reads the tree directly).
5. The app is non-sandboxed in its current shape (it reads/writes `~/.tandem/` directly — the `StoreWatcher` precedent); FSEvents on `~` needs no entitlements. If the app ever becomes sandboxed, watching `~/.tandem` would require a security-scoped bookmark — out of scope for v1, but the spec should say the watcher assumes non-sandboxed.

## 5. Scale check (hundreds of notes; up to a few hundred KB each)

**Worst-case framing.** 500 notes × 300 KB = 150 MB of markdown. No technology in this report loads that much into one process as *rendered* content — the question is only what gets held and re-parsed:

| Workload | Where it lands | Verdict |
|---|---|---|
| Editor buffer (one open note, up to ~300 KB) | CM6 `EditorState` doc — immutable, structure-sharing tree ([CM6 Reference Manual](https://codemirror.net/6/docs/ref/)) | Trivial. Obsidian runs CM6 at exactly this scale and beyond (vaults of thousands of notes). |
| Highlighting the open note | CM6 language facet, viewport + margin beyond | Trivial; off-screen lines are styled lazily. |
| Live-preview decorations | Recomputed from the incremental Lezer tree per transaction | Trivial — `@lezer/markdown` re-parses the dirty region, not the whole document (§2). |
| Vault index (wikilinks, backlinks, search) | In-process `swift-markdown` AST per note, updated on FSEvent batches | 150 MB total is bulk-parseable (cmark-gfm README benchmark, §3: a *War and Peace*-sized document in ~127 ms on a ten-year-old laptop); incrementally it's a few notes per event batch. |
| Rendered split-view pane (fallback path only) | MarkdownUI/Textual for one open note | 300 KB of markdown → thousands of SwiftUI text views; the one case worth profiling, and it's the fallback, not the primary path. |
| WKWebView process memory | One WebKit content process | Constant, independent of vault size. |

**Pressure points for the spec:** (1) never hold vault-wide *rendered* output in memory — index only (AST/metadata); (2) search/index must be incremental off the FSEvent batches, with the full rebuild at launch as a bounded, batched background job; (3) "up to a few hundred KB" per note is comfortable for CM6, but the spec should set a soft ceiling or warning around ~1 MB per note, where decoration recompute and IME composition deserve profiling before promising smoothness; (4) a few hundred files is a non-issue for FSEvents at `FileEvents` granularity (§4).

## Notes for the spec author

**Bridging (WKWebView ↔ Swift).**
- The webview is the *only* editor surface; the app owns the file system. JS→Swift via `WKScriptMessageHandler` (e.g. `note:loaded`, `note:dirty`, `link:opened`, `file:pick`); Swift→JS via `callAsyncJavaScript` (e.g. `setDocument(path, text)`, `insertText`, `revealLine`). The JS side must have **no file or network access** — everything crosses the bridge.
- Ownership: raw markdown text is the source of truth, both on disk and in the JS buffer; the decoration layer is view-only (the first invariant from Atomic Editor's architecture doc, §2).
- Autosave: JS emits dirty state + debounced text; Swift performs the atomic write (`.tmp` + rename — the same pattern the todos store already uses) and records the write for the self-write dedup in the FSEvent handler (§4, item 2).
- Links: intercept navigation (custom protocol / `willNavigate`) so `wikilink:` and `tandem://` clicks reach Swift and the webview never leaves the bundled editor page.
- Loading: `WKWebView.loadFileURL(_:allowingReadAccessTo:)` ([Apple docs](https://developer.apple.com/documentation/webkit/wkwebview)) pointed at the Resources subdirectory holding the editor page — no HTTP server required (that is precisely the Monaco failure mode, §2).

**Packaging.**
- The editor surface is a small static bundle: one `index.html`, one prebuilt JS bundle, one CSS file. Build it with esbuild (a one-liner reproduces the measured size, §2); pin the dependency set in a checked-in `package.json` + lockfile — **npm metadata is the source of truth** for versions, since the CodeMirror GitHub org's repositories are archived mirrors (source moved to [code.haverbeke.berlin](https://code.haverbeke.berlin/codemirror/lang-markdown) in 2026-04; npm remains the distribution channel and is actively published).
- Place the prebuilt bundle under the GUI target's `resources:` ([SwiftPM package resources docs](https://swift.org/documentation/package-resources)) so it ships in the app bundle and is loadable by `loadFileURL`.
- Pin the exact versions measured: `codemirror` 6.0.2, `@codemirror/state` 6.7.6, `@codemirror/view` 6.43.14, `@codemirror/language` 6.13.1, `@codemirror/lang-markdown` 6.5.2, `@lezer/markdown` 1.8.0. CM6 6.x is stable (semver-major frozen at 6), but pinning makes the bundle reproducible.

**License.**
- CM6 + Lezer: **MIT** — bundling is unrestricted; keep the license text in the bundle.
- swift-markdown: **Apache-2.0** (keep NOTICE); cmark-gfm (its C backend): **BSD-2**.
- MarkdownUI / Textual (fallback path only): **MIT**.
- Nothing GPL/AGPL anywhere in the recommended stack.

**Open decisions for the spec (not answerable by this research).**
1. **Live-preview aggressiveness.** Full inline (Obsidian's default "Live preview" editor mode — [Obsidian Help, Editor settings](https://help.obsidian.md/Editing+formatting/Editor+settings)) vs. a focus-style compromise where only the active line/paragraph renders and the rest is dimmed source (the [codemirror-markdown-hybrid](https://github.com/tiagosimoes/codemirror-markdown-hybrid) variant). Suggestion: spec a user toggle, default full inline; the CM6 decoration engine supports both with the same architecture.
2. **Wikilinks + backlinks.** CM6 has no built-in wikilink support: a small custom language extension (linkify `[[...]]`, resolve against the swift-markdown index, decoration for broken links) plus the in-process index. Scope for a follow-up ticket.
3. **Conflict policy** for an external change landing on a dirty buffer (§4, item 3).
4. **Read-only/preview surface** (if the spec wants one beyond the editor): Textual (forward-looking) vs. MarkdownUI (battle-tested, frozen).
