# 03 - Wikilink model: resolution, broken links, rename

Type: grilling
Status: resolved

## Question

Pin down the `[[wikilink]]` model the bikeshed editor implements, so the spec has one normative definition:

1. **Resolution**: by filename (basename, case-sensitive or not?) or by relative path? Duplicate basenames in different folders — allowed, and how disambiguated (path-qualified syntax, first match, error)?
2. **Syntax**: plain `[[note]]` only, or also aliases `[[note|display text]]` and heading targets `[[note#Heading]]`?
3. **Broken links**: how do they render in live preview, and what does a click do (create a note with that name? nothing? a hint)?
4. **Rename**: renaming a note is a file rename. Do wikilinks in *other* notes update to follow (Obsidian rewrites references — a multi-file write)? If yes, define exactly: which files are touched, in what order, and what happens if the rewrite is interrupted.
5. **Where links live**: wikilinks render inline in live preview; in plain source mode they are just text — confirm that is the model (no link UI in source mode).

The answer is the normative wikilink section of the spec.

## Answer

Resolved by grilling (Q1–Q9, all accepted). Normative model:

**Resolution** — A wikilink's target names a *note* (a `.md` file); resolution is computed live from the current vault file set (derived state — no stored link index). A **bare target** matches the note's basename (filename minus extension), case-insensitive, and resolves iff **exactly one** note matches; zero or multiple matches → **broken link**. A **qualified target** is a vault-root-relative path, matched case-insensitive against the note's vault-root-relative path; same exactly-one rule. Notes only: `[[photo.png]]` is broken — attachments live in the vault (vault protocol) but are referenced by relative path from the referencing note, never by wikilink. `[[…]]` inside fenced code blocks or inline code is not a link. Consequence: **creating or deleting notes never rewrites any link** — a broken link starts resolving the moment the note appears; only rename rewrites link text. Corner case tolerated, not special-cased: on a case-*sensitive* volume, case-variant duplicate names make any link to that name ambiguous → broken.

**Grammar (v1)** — `[[target[#fragment][|alias]]]`: split at the first `#`, then the first `|`; scan left-to-right, first `]]` closes. **Display text** = alias if present, else fragment if present, else the target as written. The fragment is parsed and stored but **inert in v1**: `[[note#Heading]]` displays "Heading" but the click opens the note at the top — no heading matching, no scroll (v2 candidate; `#^id` treated the same). **Not links** (literal text): unclosed `[[` at end of line/file, empty or whitespace-only target, same-note form `[[#Heading]]`, and embeds `![[…]]` (out of scope in v1). The app never creates note names containing `#` or `|` (vault protocol reserves `#` for heading targets; `|` is reserved the same way — the grammar splits targets on both), which keeps the grammar unambiguous for app-created names. A note whose on-disk name contains `#` or `|` — only possible via agent/external creation — is **unnameable by wikilink**: any `[[…]]` mentioning it splits into a fragment/alias and resolves elsewhere or breaks; the spec tells agents to keep names free of both. (Answers the item-1 deferral in ticket 04.)

**Broken links** — Rendered visually distinct but unobtrusively (exact style is ticket 02 / spec's); clickable. **Click creates an empty note at the link's path and opens it** — bare → vault root; qualified → that path, creating folders as needed; no confirm dialog. Clicking a resolved link opens the target note.

**Rename / move** — One operation: "change the note's path" (rename and folder-move are the same). **The app rewrites every wikilink that resolves to the renamed note** — in all vault notes, including the note itself (self-links), in any form: bare, qualified, aliased (the alias's display text is preserved; only the target portion changes). **Wikilinks only**: markdown links `[text](…)` are never rewritten — they stay the agent's responsibility (spec guidance: use wikilinks); embeds are literal text, untouched. Each rewritten target is written in the **canonical form for the new file set** — bare if the name is unique, vault-root-qualified if not (so a qualified link drops its path when a rename makes the name unique, and a bare link gains a path when a rename makes it ambiguous). Links that don't resolve to the renamed note — broken ones included — are never touched. **Only app-performed renames rewrite**: an agent renaming a file on disk leaves stale links, which become visible broken links (Obsidian parity). Mechanically, per the vault protocol ([ADR 0004](../../../docs/adr/0004-vault-protocol.md)): **one transaction under the bikeshed's sidecar lock, no journal** — each referencing note is rewritten first (per-file temp + fsync + `rename`, atomic per file), then the note file itself is renamed (a single atomic `rename(2)`, valid across folders on the same volume). A crash mid-sequence: `flock` releases, no torn writes, no data loss, at most some links point at the new name while the note is still at the old one — they render as broken, and **re-running the rename self-heals** (the note is still at the old name, so the rewrite scan finds them again). No auto-repair in v1; the retry is the repair. New name already taken → **refuse with an error, nothing written** (no overwrite, no silent suffix). Deletion (mechanism is ticket 04's) rewrites nothing: links to a deleted note become broken. Rewriting is grammar-level text substitution over the note's **body** — it needs no full markdown parse. The YAML frontmatter block is out of scope: per the vault protocol it is opaque and the app never rewrites it, so a wikilink inside frontmatter is not updated on a rename (it goes stale; the agent or user manages it).

**Backlinks (data model)** — For the open note, its backlinks are the vault notes containing at least one wikilink that resolves to it; broken links contribute nothing. What the panel lists and where it lives is ticket 02's.

**Source mode** — Plain text: no click, no hover, no resolution. Markdown syntax highlighting may color wikilink tokens (editor highlighting, not link UI). The model is view-independent — a wikilink is syntax the preview layer resolves and renders — so it holds for inline preview, the split-view fallback, and source mode alike. Any future link-inserting UI (e.g. `[[` autocomplete from tickets 01/02) writes the canonical form.
